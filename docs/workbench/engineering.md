# 工程实施复盘

## 实际改动

复用原 Python / FastAPI / SQLAlchemy / Streamlit 架构、Decimal 精确指标、UTC 范围校验、证据登记、规则报告和原始重放。将旧 UI 保留为高级工程入口；新增中文主流程，将“判断、证据、下一步”放在图表和调试数据之前。

`CommunicationBundle` 从持久化报告及冻结证据生成中文、英文、问题单和结构化下载，不重新诊断或另算指标。导出前核查证据内容寻址 checksum、来源/版本/窗口及报告事实引用；异常时拒绝导出正常结论。

新增 `POST /recoveries`，只接受已有报告 ID，从报告推导时间窗与来源；用既有 Evidence 表存储恢复回执，关联前后报告。重放完成、恢复后检查未发现问题、仍未解决与失败分开。`GET /investigations/{run_id}/communication?recovery_id=...` 拒绝无关报告关联。

UI 按标准化上下文、问题和模式绑定结果，范围改变时撤下旧说明与下载。原始报告固定为历史版本。CLI `demo --output` 可以把本次证据写入新位置，不覆盖旧默认产物。启动脚本补齐缺失/延迟场景准备的退出码检查。

## 实际验证与修正

改造前本次只读基线为 78 个离线测试通过，Ruff 和 54 个文件格式检查通过。最终结果单独见[本轮记录](../verification/workbench-2026-11-13/final/results.json)，不能用这组基线数字冒充新增功能验证。

真实 HTTP 检查与恢复在独立 SQLite 演示库中执行，得到预期的固定案例数据，原报告内容保持不变。原始 CLI 复现与新增 HTTP 工作流分别留档。[HTTP 摘要](../verification/workbench-2026-11-13/http-release/summary.json)、[CLI 产物](../verification/workbench-2026-11-13/demo-result.json)。

开发中发现：PostgreSQL NUMERIC(78,30) 返回更多尾零，新增测试一度错误要求与 SQLite 完全相同的字符串；改为精确 Decimal 等值判断。业务导出仍严格保留各自报告的原始字符串，避免在渲染层改变数值口径。没有为匹配历史数字修改计算逻辑。

浏览器自检发现普通流程把质量详情渲染成 JSON，改为缺失分钟和时间的可读列表；执行状态也补齐中文标签。上述修改来自代理自检，不包装成真实用户反馈。关键失败路径使用故障注入自动化验证，不声称实际发生了外部服务事故。

## 设计取舍

- 用确定性模板确保双语的数字、单位和证据引用一致，不引入模型成本、密钥或新的诊断逻辑。
- 恢复回执复用证据表；不增加工单平台、账号系统、前端框架或数据库迁移。
- 保留旧报告便于审核；条件变化时要求重查，而不是把旧结论静默重算为“最新”。
- 恢复可以复用已存在的完整版本；内容寻址版本复用不代表本次恢复动作未被记录。
- 本地单人演示优先；缺少后台恢复任务、分布式并发租约、认证和生产监控，不能直接作为公网服务使用。
